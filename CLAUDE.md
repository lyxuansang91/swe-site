# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

MkDocs Material site that publishes four sibling content repos as one site at
[swe.springlee.dev](https://swe.springlee.dev) (Cloudflare Pages, Direct Upload via
GitHub Actions). This repo holds **only build config** — `mkdocs.yml`, `build.sh`,
`scripts/`, `docs/index.md`, `docs/SUMMARY.md`.

Sections and their source repos:

| Section | `docs/` dir | Source repo | Nav |
| ------- | ----------- | ----------- | --- |
| LeetCode Algorithms | `leetcode/` | `leetcode-algorithms` | generated `SUMMARY.md`, converted |
| SWE Interview | `swe/` | `swe` | hand-maintained `SUMMARY.md`, converted |
| System Design | `system-design/` | `system-design-notes` (our fork of `liquidslr/system-design-notes`) | generated by `scripts/gen_nav.py` |
| Real Interview Questions | `real-interview-questions/` | `real-interview-questions` | hand-maintained `SUMMARY.md`, converted |

## Critical rule

Everything under `docs/` except `index.md`, `SUMMARY.md` and `javascripts/` is
**generated by `scripts/prepare.sh` and wiped on every run** (`rm -rf docs/leetcode
docs/swe docs/system-design docs/real-interview-questions`). Never edit content
there — edit the content repo and re-run `prepare.sh`. `site/` is build output.

## Local development

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
bash scripts/prepare.sh          # uses the sibling checkouts when all four exist
.venv/bin/mkdocs serve           # http://127.0.0.1:8000
```

`prepare.sh` falls back to `git clone` (the CI path) if **any** sibling checkout is
missing — so a partial set of siblings silently builds from GitHub instead of your
working tree.

## Adding a section

1. `scripts/prepare.sh` — add a `<NAME>_REPO` default, extend the sibling-checkout
   test and the clone branch with a `<x>_src`, add the dir to the `rm -rf` /
   `mkdir -p` lines and to the final page-count `find`, then copy the markdown and
   emit `docs/<section>/SUMMARY.md` via `scripts/convert_summary.py`.
2. `docs/SUMMARY.md` — add the tab; `docs/index.md` — add the section bullet.
3. `README.md` — document the section and its env-var override.
4. In the content repo: `.github/workflows/trigger-site-deploy.yml` (copy `swe`'s)
   plus the `SITE_DISPATCH_TOKEN` secret, so its pushes rebuild the site.

Copy blocks exclude the source repo's own `SUMMARY.md` (it is converted, not copied)
and its `CLAUDE.md` (repo maintenance docs don't belong on the site).

## Gotchas

- Content uses GitBook-style `$$...$$` math, rendered client-side by KaTeX
  auto-render (`docs/javascripts/katex.js`) — not a Python markdown extension.
- Only an exact `README.md` becomes a directory index in MkDocs. `prepare.sh`
  normalises the `Readme.md`/`README.md` mix in `system-design` for that reason.
- MkDocs skips dot-directories, so the LeetCode repo's `.gitbook/assets` is copied
  to `_assets/` and the links are rewritten by `sed`.
- Deploys run from GitHub Actions (`.github/workflows/deploy.yml`), **not** from
  Cloudflare's Git integration — don't also connect this repo in the Cloudflare
  dashboard, or every change builds twice.
- Because of that, a Cloudflare Pages **deploy hook** cannot rebuild this site.
  It has no repo to clone and no build command to run, so it re-serves the assets
  already uploaded and returns `success: true` while the content stays stale.
  Content repos must fire `repository_dispatch: content-updated` at this repo
  instead — that is the only trigger that runs `build.sh`. If a content push
  didn't reach the site, check the content repo's trigger workflow first.

## Verifying a change

```bash
bash scripts/prepare.sh && .venv/bin/mkdocs build --strict
```

Then check the section landed: `ls site/<section>/`.
